# Natural Language Querying (NLQ) — Spec

## Objective

Enable **Branch Managers** to query YMCA attendance/schedule data using natural language and receive:
- A clear answer (text summary)
- A table of results (for auditability)
- Optional chart suggestions (for KPI-style questions)

This feature is **read-only** for MVP.

---

## Why NLQ (from the PRD)

The PRD emphasizes:
- KPI dashboards and exports
- Fast reporting and analysis
- Reduced manual effort

NLQ complements dashboards by enabling ad-hoc questions without building a new screen every time.

---

## Non-goals (MVP)

- Writing/modifying data via NLQ (no INSERT/UPDATE/DELETE)
- Free-form SQL execution from the model
- Access outside the user’s allowed scope

---

## Security model (must-have)

### Baseline rules
- **Read-only only**
- **Scope is enforced by Supabase RLS and/or explicit server authorization checks**
- **No raw SQL** generated by the model is ever executed directly
- **Branch scope:** the query must be constrained to the authenticated manager’s **single branch**.

### Execution options

**Option A (preferred): “Semantic RPC”**
- Create a set of **RPC functions** that represent approved queries:
  - `kpi_monthly_totals(branch_id, month_start)`
  - `kpi_instructor_utilization(branch_id, month_start)`
  - `attendance_by_day(branch_id, month_start)`
  - `attendance_by_class_type(branch_id, month_start)`
- LLM output is a JSON “plan” selecting an RPC + validated params.
- Server calls Supabase RPC using user session (RLS applies).

**Option B: “Whitelisted Views”**
- Create read-only **views** (or materialized views) and allow the model to pick:
  - view name (from allow-list)
  - filters (branch_id, month, instructor_id, class_id)
  - ordering and limit
- Server builds the query with safe parameterization.

### Service-role key guidance
Avoid using a service-role key. If used, it must be paired with:
- strict authentication
- strict role checks (manager/regional)
- strict branch scoping
- strict allow-list of queries

---

## Architecture (recommended)

### Components
- **UI**: “Ask a question” panel in the web dashboard
- **API**: Next.js route handler `/api/nlq`
- **LLM**: converts question → structured query plan (JSON)
- **Executor**: calls Supabase RPCs / views and returns results

### Response shape (suggested)
- `answer`: short text
- `queryPlan`: structured plan (for debugging/audit)
- `data`: table rows + column schema
- `chartSuggestion`: optional (type, x/y keys)

---

## Prompting strategy

### Inputs to the LLM
- User role + allowed branch ids
- Supported “query types” (RPC names)
- A short schema summary (table names + key fields)
- The natural language question

### Output constraints
- JSON only
- Must match Zod schema
- Must choose one approved query type

---

## Example questions (MVP)

- “Total attendance for Eastside in September 2025”
- “Average attendance per class type last month”
- “Which instructors have the highest utilization this month?”
- “Show daily attendance trend for October”
- “What locations are available today for a 30 minute meeting outside scheduled class times?”

## Decisions

- **Audience (initial):** Branch Managers only
- **Branch scope:** Manager’s branch only (no cross-branch)
- **Provider:** OpenAI

---

## Branch scoping (implementation guidance)

**Rule:** Never allow the model to choose a branch.

- The server determines `branch_id` from the authenticated manager’s profile/claims.
- The server injects that `branch_id` into the query plan (RPC params / view filters).
- If the user asks “compare branches…” respond with a refusal like “NLQ is limited to your branch.”

## “Meeting availability” queries (new NLQ capability)

### Example
User: “Tell me what locations are available today for a 30 minute meeting outside scheduled times.”

### Required clarifications (if not provided)
- **Business hours window** (e.g., 06:00–21:00). If omitted, use a branch default.
- **Timezone**: “today” is based on the branch timezone.
- **Buffer** (optional): minutes before/after classes to avoid back-to-back bookings.

### Data sources (current + minimal additions)
To answer this safely and deterministically, we should treat “availability” as **free time not occupied by scheduled classes**.

- **Existing**: `locations` + scheduled class times (currently modeled via `class_sessions` with `day_of_week`, `start_time`, `end_time`, `schedule_id/effective_month`).
- **Recommended additions** (minimal):
  - `branches.timezone` (IANA name like `America/New_York`)
  - `branch_hours` table (branch_id, day_of_week, open_time, close_time) OR a single default window in config.

### Execution pattern (RPC-only, whitelisted)
Add a read-only RPC that returns available time windows:

- `available_locations_for_meeting(p_branch_id uuid, p_date date, p_duration_minutes int, p_buffer_minutes int)`
  - **Returns**: list of `{ location_id, location_name, start_time, end_time }` slots (or “first available” per location)
  - **Server enforcement**:
    - `p_branch_id` is **injected server-side** from manager’s branch (never from the model)
    - date is normalized to the branch timezone “today” unless user specified a date

### Notes / limitations (MVP)
- This does **not** account for other meetings unless we later add a `meetings`/`events` table.
- Availability is “free relative to class schedule”, not a full booking system (yet).
